✅ **CPU-GPU micro-mastery remediation & draw-call collapse (Phases 0–3, 5, and 4.1–4.2)** — **done and verified (2026-08-25)**, implementing [CPU_GPU_MICRO_MASTERY_REMEDIATION_PLAN.md](../../../../plans/CPU_GPU_MICRO_MASTERY_REMEDIATION_PLAN.md); the plan's own document is unchanged, this entry records what landed. **Phase 0 (trustworthy measurement):** `webgpu_micro_mastery_lag_test` now gets the same `RUN_SERIAL`/`TIMEOUT 300`/`LABELS "lag"` treatment as `frame_lag_test` (`CMakeLists.txt:312`), plus its own calibration-normalised, drift-guarded timing verdict and baseline file (`tests/singularity/webgpu_micro_mastery_lag_baseline.txt`) — two consecutive standalone runs landed within 0.1% of each other. **Phase 1 (pipeline cache):** `WebGpuRenderer::bindPipeline` binds only on an actual change; the four unconditional `SetPipeline` sites now route through it. **Phase 2 (correctness):** `TessMesh` gained a `revision` counter and `GpuMeshCache` checks it alongside `id`, closing the in-place-edit staleness gap the header already claimed was closed (no current writer needs it — every writer today replaces the whole `TessMesh` by value, which already gets a fresh `id` — but it makes the class's documented contract true and guards a future sculpt/deform tool, the same failure shape the Pottery tool already hit for FaceTexture); `GpuBufferPool::init()` now calls `shutdown()` first so a second init (device loss/resize) cannot leak the previous device's chunks. **Phase 3 (guard the claims):** `gpu_mastery_test` gained a device-backed section ([4a]–[4e]) covering cross-frame chunk saturation, `init()` not leaking, the reincarnation fix, frame-based GC, and the revision guard — verified by reading buffer *contents* back (`WGPUBufferUsage_CopySrc` added to the mesh cache's vertex buffers for exactly this), not by comparing `WGPUBuffer` pointers, which the driver is free to recycle after a release. **Phase 4.1–4.2 (draw-call collapse, rung one):** `Object::drawCube` now merges all six faces into one `drawMesh` call when every face resolves identical paint (the common, unpainted case), decided fresh every draw from the resolved albedo — never cached on the Object, so one `setFaceColor` stroke drops straight back to the six-draw path (guarded in `webgpu_object_test`). **Phase 5 (channel honesty):** the seven derived `@screen-channel` metrics are now `ComputedProperty` with a null setter (read-only; `wireframe` stays writable — it drives the rasterizer); `vramAllocatedBytes`/`uniformBytesWritten` are `double` end to end. Three doc sentences corrected in `CPU_GPU_MICRO_MASTERY.md`: the linear search does not saturate memory *within* a frame (only across frames, via `resetFrame()` resetting `currentIdx`), and the pool is a per-frame bump allocator safe only because WebGPU orders queue writes against submitted command buffers — a direct Vulkan/Metal port would corrupt. **Measured effect** (`webgpu_micro_mastery_lag_test`, 4,500 objects): draw calls 19,500 → 4,500/frame, `pipelineSwitches` ~19,500 → 2/frame, average frame time ~175 ms → ~104 ms. Still short of §1's 10,000-object/60 FPS telos — that's Phase 4.3. Suite is 70/70. **Scope note (2026-08-26):** every phase above is delivered and the measurements hold — but at real world sizes the GPU submission path these phases optimized was never the binding term. `frame_lag_test` puts `Zone::update` at 40 ms against `LawManager::tick`'s 0.74 ms at 512 objects; submission is a rounding error beside it. The heavy probe looked excellent because 4,500 objects is where submission finally dominates, and no Person's world has 4,500 objects. This work is prerequisite and will matter when a menu really is 10,000 beings (`CPU_GPU_MICRO_MASTERY.md` §1), but it did not and could not fix a frame that is CPU-bound in world update. See the `Zone::update` scaling item below.
