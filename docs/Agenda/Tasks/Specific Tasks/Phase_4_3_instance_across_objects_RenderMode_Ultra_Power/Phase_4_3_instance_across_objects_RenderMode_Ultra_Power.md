✅ **Phase 4.3 (instance across objects) + `RenderMode` + Ultra Power test** — **done and verified (2026-08-26)**, implementing the plan Zach posted (instancing architecture + `renderMode` + `EARTHCALL_ULTRA_POWER`). The reasoning for why batching does not cross the six refusals is written out in `CPU_GPU_MICRO_MASTERY.md` §6, per the plan's own AUTHOR flag, before landing rather than after. Two corrections made to the plan as posted (both factual, not preference): `wgpuRenderPassEncoderDrawIndexed` does not fit — there is no index buffer anywhere in this renderer (`TessMesh` is triangle-soup), so instancing uses non-indexed `wgpuRenderPassEncoderDraw(vertexCount, instanceCount, ...)`; and the mesh shader to edit is `kMeshWGSL` inline in `WebGpuRenderer.cpp`, not `smoke_mesh.cpp` (an unrelated Milestone-5 smoke test with its own disposable shader). **Instancing:** `WebGpuRenderer::drawMesh` resolves the draw's albedo immediately (a queued batch cannot hold `RenderMaterial::albedoPixels`, documented valid only for the draw call) and queues `{model, normalMat}` into `_meshBatches`, keyed by `(mesh identity, albedoView, baseColor, shading)` — everything that must be identical for one instanced draw to render every member correctly. `endFrame()` calls the new `flushMeshDraws()`, which turns each group into one `wgpuRenderPassEncoderDraw` with `instanceCount` = group size, reading a per-instance `{model, normalMat}` array from a `suballocateStorage` buffer via `@builtin(instance_index)` in `kMeshWGSL`. `@screen-channel.drawCalls` still counts real driver draw calls (once per batch), not once per instance. **New invariant documented, not yet enforced:** queued `TessMesh*` pointers must outlive `flushMeshDraws()` at `endFrame()` — true today (nothing destroys an Object between the draw loop and `endFrame()` in `EngineRender.cpp`) but was not a requirement before deferred batching; see the comment at `_meshBatches` in `WebGpuRenderer.hpp`. **Known limitation, not a regression:** batches aren't sorted back-to-front, so translucency ordering is unaddressed — the immediate-mode path being replaced had no such sort either. **`RenderMode`:** `ObjectTypes::RenderMode` (`Auto`/`Analytic`/`Mesh`, append-only int like `ShapeKind`) gates `drawSmoothModel`/`drawComplexModel`'s existing analytic-vs-mesh choice; `Mesh` opts a Law out of the exact raymarched path, exposed Law-writable as `@object.renderMode`. **Does not currently batch a population of identical shapes** (corrected an overstated first draft of `CPU_GPU_MICRO_MASTERY.md` §7 during review): `_smoothMesh` is a per-Object member, so N separately-authored identical spheres own N distinct `TessMesh`s at N addresses, and §6's batch key groups on mesh *pointer* identity — `RenderMode::Mesh` on such a population produces N batches of size 1, not one instanced draw. It genuinely batches only where Objects already share one static mesh instance (the merged-cube case). A content-addressed tessellation cache is what would be needed to extend real instancing to analytic shapes; not built here. **Ultra Power:** `EARTHCALL_ULTRA_POWER=1 ./build/webgpu_micro_mastery_lag_test` (or `ctest -R ... -V`) scales the population to 48,000 meshes + 2,000 fields (50,000 total) — asymmetric on purpose, not a straight 10x of both, see the finding below. A quarter of the fields cycle through a `SmoothUnion` CSG box/sphere melt, a genuinely `OntoMath::Piecewise`-driven sinusoidal manifold (`Piecewise::continuous` wrapping a compiled `sin/cos` `MathNode`, not just the plain string-expr path), and alternating extent 1000.0/0.01 for scale-variance stress; informational only (not judged against the standard-scene baseline — that would be comparing a 50,000-object frame to a 4,500-object number, the same category error Phase 0 exists to prevent) with its own 600s hard ceiling. Never runs under plain `ctest`. **A real pre-existing cost, surfaced while sizing this:** `Object::setFieldShape` → `rebuildGeometryCaches()` unconditionally tessellates a Field object's mesh (`_fieldMesh = geom::tessellateSdf(...)`) even under WebGPU, which never reads it (`drawFieldModel` raymarches exactly instead) — measured 30-100ms per field object depending on shape complexity, meaning even the *standard* 1,500-field scene spends real construction time on a mesh nothing draws. This is pre-existing engine behavior this session did not introduce or change (both the standard scene's field count and `setFieldShape`'s eager-tessellation are untouched), but it is why ultra power's field count stays at 2,000 rather than 10x'ing to 15,000 — that would cost 15+ minutes on construction alone before a single frame renders. Cubes pay none of this cost (no branch for `ShapeKind::Cube` in `rebuildGeometryCaches`), which is why the "ultra" scale lives in the mesh count instead, where it also happens to be exactly what stresses the new instanced-batch path. Worth a follow-up: making Field-object construction lazy about `_fieldMesh` under a backend that never reads it. **Verification:** `webgpu_object_test`'s pixel readback is byte-identical before/after instancing (painted/green/unpainted/field cases); `gpu_mastery_test` 32/32; `webgpu_sdf_parity_test` 20/20 exact; `webgpu_particle_test` unaffected — all confirming the batched path renders identically to the old immediate path, not just that it runs. Measured on the heavy probe: draw calls 4,500 → 1,501/frame (3,000 identical cubes collapsed to ONE instanced draw). Ultra power ran clean: `drawCalls: 2001` (the 48,000 cubes — all sharing `mergedCubeMesh()` with default paint — collapsed to exactly 1 instanced draw; the 2,000 CSG/Piecewise/extreme-scale fields drew individually as expected), 20 frames in 20.9s wall (machine calibration x2.29), no crash. **Left for a future pass:** the machine this landed on was shared with several other concurrent processes (browser, IDE, other agent sessions) at verification time, which pushed both `frame_lag_test` (untouched, pre-existing) and `webgpu_micro_mastery_lag_test` into LAG under a *stable-but-slow* calibration their drift-guard correctly did not catch (the guard catches a machine that *moved* during measurement, not one that started slow and stayed slow) — re-run both on a quiet machine to confirm; `frame_lag_test` failing too, on code this session did not touch, is the evidence this is environmental, not a regression from this work. Re-run once the machine settled: `ctest --test-dir build -j4` came back 70/70, including both lag tests, in 80s total (vs. the earlier contended run's 569s) — resolved, not a standing concern.
