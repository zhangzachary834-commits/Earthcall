⚑ AUTHOR — **Phase F (Hi-Z pre-pass) needs a bigger change than scoped, not yet built.** Investigated 2026-09-01 while implementing Phase C. The plan assumed adding "a new, earlier `wgpuCommandEncoderBeginRenderPass`" before the existing scene pass — but `WebGpuRenderer::beginFrameOffscreen` opens the ONE scene pass immediately, before any `drawMesh`/`drawImplicit` calls happen; mesh and SDF draws are deferred into `_meshBatches`/`_sdfBatches` and only actually recorded at `endFrame()` (`flushMeshDraws()` then `flushSdfDraws()`, into the SAME already-open pass). So there is no moment where "the opaque occluders for this frame" are both fully known AND the scene pass hasn't opened yet, without restructuring when that pass opens. And ordering mesh draws before SDF draws *within* the current single pass does NOT give the Hi-Z benefit anyway — the SDF pipeline's own `discard` + `frag_depth` write disable per-draw early/Hi-Z rejection for its OWN fragments regardless of what already-written depth precedes it in the same pass, which is exactly the caveat the addendum already carried ("a discarding shader disables early-Z... has to be a separate, non-discarding pass"). A correct implementation needs either (a) deferring `_pass`'s opening until `endFrame()` (breaks every immediate-mode verb that writes directly to `_pass` mid-frame: `drawLines`, `drawOverlay`, `drawSolid`, `drawTris2D`, `drawLines2D`, `drawImage2D`), or (b) a genuinely separate pre-pass driven explicitly from `EngineRender.cpp`'s object loop (a first pass over `objects` calling a new depth-only draw verb for the mesh-shaped opaque subset, before `beginFrameOffscreen` opens the main pass) — which requires correctly re-deriving, without duplicating incorrectly, exactly which objects `Object::drawObject()` will draw as an opaque mesh THIS frame (on WebGPU, `rendersImplicitExactly()` is true, so most smooth/complex/field objects actually go through `drawImplicit`, not `drawMesh` — only polyhedra, Bezier patches, and legacy Cube/2D shapes reliably take the mesh path; getting this occluder set wrong risks a real visibility bug, not just a missed optimization, since it writes into the SHARED depth buffer). Zach's call on whether (a) or (b), and whether it's worth the added surface area for what the addendum itself calls a "cheap, no semantic risk" phase that turns out not to be cheap to build safely.
