- ⚑ AUTHOR — **Phase F (Hi-Z pre-pass) needs a bigger change than scoped, not yet built.** Investigated 2026-09-01 while implementing Phase C. The plan assumed adding "a new, earlier `wgpuCommandEncoderBeginRenderPass`" before the existing scene pass — but `WebGpuRenderer::beginFrameOffscreen` opens the ONE scene pass immediately, before any `drawMesh`/`drawImplicit` calls happen; mesh and SDF draws are deferred into `_meshBatches`/`_sdfBatches` and only actually recorded at `endFrame()` (`flushMeshDraws()` then `flushSdfDraws()`, into the SAME already-open pass). So there is no moment where "the opaque occluders for this frame" are both fully known AND the scene pass hasn't opened yet, without restructuring when that pass opens. And ordering mesh draws before SDF draws *within* the current single pass does NOT give the Hi-Z benefit anyway — the SDF pipeline's own `discard` + `frag_depth` write disable per-draw early/Hi-Z rejection for its OWN fragments regardless of what already-written depth precedes it in the same pass, which is exactly the caveat the addendum already carried ("a discarding shader disables early-Z... has to be a separate, non-discarding pass"). A correct implementation needs either (a) deferring `_pass`'s opening until `endFrame()` (breaks every immediate-mode verb that writes directly to `_pass` mid-frame: `drawLines`, `drawOverlay`, `drawSolid`, `drawTris2D`, `drawLines2D`, `drawImage2D`), or (b) a genuinely separate pre-pass driven explicitly from `EngineRender.cpp`'s object loop (a first pass over `objects` calling a new depth-only draw verb for the mesh-shaped opaque subset, before `beginFrameOffscreen` opens the main pass) — which requires correctly re-deriving, without duplicating incorrectly, exactly which objects `Object::drawObject()` will draw as an opaque mesh THIS frame (on WebGPU, `rendersImplicitExactly()` is true, so most smooth/complex/field objects actually go through `drawImplicit`, not `drawMesh` — only polyhedra, Bezier patches, and legacy Cube/2D shapes reliably take the mesh path; getting this occluder set wrong risks a real visibility bug, not just a missed optimization, since it writes into the SHARED depth buffer). - **Incremental Action Nodes (TREAT/LEAPS-style RHS incrementality)** — Zach's observation (2026-08-28, after reading Fable 5's [Green Hills §3](../../Reflections%20on%20Earthcall%27s%20Progression/Reflections%20on%20Trajectory/Green_Hills_Population_One.md)): the Rete incrementalizes the *condition* side beautifully — `evaluateDirty()` and compiled terminals mean only changed facts re-evaluate — but the *action* side has no equivalent. A WhileTrue law whose conditions hold for 50 subjects calls `action.run()` for all 50 every frame, even when inputs haven't changed and the output would be identical. A `Set` writing `position := vec3(0,0,0)` to a subject already at `(0,0,0)` does the full path-resolve → read → compute → write → trace cycle 60 times a second; the `skipAudit` flag (`Law.cpp:464`) suppresses the *log* but not the *work*. The solution is extending the Rete's incremental principle from condition selection to action execution — what the production-system literature calls TREAT and LEAPS (Lazy Evaluation of Actions in Production Systems). Concretely: (1) **Input-dirty gating** — an action node's inputs are the property paths it reads (Map bindings, Drive input, `@event.subject` properties); if none changed since last tick, skip the node entirely. (2) **Output memoization** — cache the last value written per law-per-subject-per-path; compare before writing; the `wrote = false` trace outcome already exists, make it the fast path instead of a post-hoc observation. (3) **Map/Flow derivative shortcut** — `Map` is `p := F(bindings)`; when a binding changes, OntoMath's `ScalarForm::derivative` can compute the delta rather than re-evaluating the full piecewise. (4) **Drive input gating** — a Drive whose input is a *property* (not the world clock) that hasn't changed can skip; the architecture already distinguishes these (`ActionNode::input`, `ActionModel.hpp:192`). Together with the condition-side Rete, this would make the idle-world cost genuinely O(changes), not O(matches). The per-law-per-subject action memo is a small struct: `{input values hash, output value}`, checked before `action.run()` in the WhileTrue reactive path (`Law.cpp:1670`).
