THE THESIS, IN ONE LINE
  A control is a being you can point at, plus a law that says what pointing at it
  means. No Button class, no ControlKind enum, no src/UI/, no UI event path.
  A control KIND is a category being; a control INSTANCE is an instance-of edge.

FOUR THINGS I FOUND BROKEN AND FIXED — check these before trusting nearby code
  1. Object::updateHoverState had NO CALLERS ANYWHERE, and published its enter edge
     TWICE (compared against _wasHoveredLastFrame, written one frame behind
     _isHovered). OBJECT_HOVER_EVENTS_SYSTEM.md documented all 199 lines of it.
  2. _isHovered / _hoverPoint were unregistered — refusal #6. Now read-only
     `hovered` / `hoverPoint` on Object.
  3. ObjectConcept::RelationTemplate dropped every edge to a being OUTSIDE the
     captured set, so an instantiated control was not a member of its category.
     Anchored relation templates (bAnchorId) fix it. This is the piece that makes
     set-to-set creation and Law meet at all — read INTERACTION_AS_LAW.md §7.
  4. DynamicPropertyBridge::setValue silently changed an AUTHORED property's TYPE
     where a registered one coerces. A Map writing 1.0 into a granted `bool` made
     every std::get_if<bool> read false. Same law text, two behaviours, decided by
     whether the property was written in C++ or granted by an author.

THE ONE THAT WILL BITE YOU
  Two laws whose actions satisfy each other's conditions are a LOOP, not a branch.
  The toggle authored as an on-law/off-law pair never moved: the on-law's write
  marks the Rete state fact dirty, which re-activates the off-law's Compare
  terminal in the next chain round, and both fire in one tick. Written up in
  LAW_AND_CREATION_SYSTEM.md §7e as well as INTERACTION_AS_LAW.md §6b.
